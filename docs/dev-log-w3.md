# W3 开发日志：文件告警能回答"谁干的"了——以及 6 个攻击用例连踩出的告警链暗坑

> 状态：草稿（待人工润色后发布）
> 本周一句话：**文件事件接上进程上下文，篡改告警从"某文件被改"进化到"某容器里某进程的某条命令链干的"；进程白名单支持 SIGHUP 热加载；攻击用例库扩到 6 个并全部双轮复跑通过；性能基线四个指标全部实测，全部未达标，数据都在。**

## 本周做了什么

**1. 文件告警能回答"谁干的"（M0-1）**。之前文件类告警只有一个路径和事件类型，进程链富化只覆盖 exec 和网络事件。这周把进程上下文（全路径、uid、完整祖先链、容器 ID）接进了文件事件和告警。验收用例：往容器里挂一个受保护的基线文件，容器内进程追加一行，告警长这样：进程 `/bin/busybox`（sh），uid 0，容器短 ID `04483772ba9b`，祖先链一层层跑回 `runc` 和 `containerd-shim`。谁在什么时间从哪条路径进来改的文件，一条 SQL 就能查清楚。

**2. 进程白名单热加载（M0-2）**。可信进程（比如我们自己的采集 agent）写受保护路径不再误报，改配置发 SIGHUP 就生效，不用重启。实现上是整代不可变快照加写锁整体替换（`src/baseline/monitor.cpp:125`），读路径无锁，热加载不阻塞事件处理。

**3. 资产清点**。**`asset collect`** 一条命令摸清机器家底：包、端口、进程、自启动、定时任务，落 SQLite 后 `asset list --type/--json` 查询。加上前两周的遥测和基线，"机器上有什么"和"机器上发生了什么"两条线都通了。

**4. 兼容矩阵的坑堵上一个**。Ubuntu 20.04（5.4）上 kprobe 降级路径实测跑通，但暴露了一个更难看的问题：降级分支不初始化遥测，配置里网络、DNS、权限开关全开着，日志却一声不吭，监控在静默中缺了半边。现在启动时会打 `[telemetry] kernel <5.8 无 ring buffer，遥测不可用，已忽略配置: ...`（`src/baseline/monitor.cpp:653`）。安全工具自己哑了，比不告警严重得多。

**5. 攻击用例库扩到 6 个**。在原有反弹 shell、读 /etc/shadow、chmod 777 之外，新增容器内执行 docker 命令（挂 docker.sock）、敏感路径批量读取、容器内篡改挂载的基线文件。每个用例是攻击脚本加预期事件核对加清理步骤，`run_all.sh` 起一次 monitor 连跑两遍。当前成绩：12/12 全过，两轮结果一致（`tests/attack-cases/`）。

## 最难的一个问题及解法

最难的不是写功能，是验收时用例连踩出三个互相纠缠的告警链暗坑，现象和根因隔着三层。

症状：读 /etc/shadow 的用例明明跑了，alerts 表却是零新增，监控日志里明晃晃写着 `[DB] Alert saved`。

排查链。第一坑：monitor 的实时告警根本不写 `--db` 指定的文件，它写死了系统库 `/var/lib/baseline-guard/baseline.db`（`main.cpp` 里 alert_db 用默认路径）。我在错误的库里数了半小时行。第二坑：我怀疑相邻用例的告警互相顶掉，给同一个文件加了第二条规则想让用例各自独立，结果整个规则直接失效。规则是按 inode 注册进 `inode_to_rule` map 的，两条规则同一个文件，后加载的把先加载的覆盖了，旧规则一整轮零告警。第三坑：节流按 rule_id 独立计 10 秒窗口，相邻用例跑同一个文件时，后跑的告警被静默吞掉，还伴随日志文案撒谎（"skip DingTalk but persist to DB"，实际节流的连库都不落，W2 修过的行为，文案没改）。

解法分两层。用例库层面：验证脚本全部改成按 rule_id 过滤、按系统库查询、对共享节流窗口的文件不做告警硬断言（事件维度断言兜底），这套约束写进了 `tests/attack-cases/README.md` 的实测发现一节。产品层面：同文件多规则覆盖、节流文案这两处记为 W4 的缺陷单，这周不动代码，先把用例跑稳。

## 实测数据

性能四指标首次全量实测，完整数据在 `docs/perf-baseline-w3.md`，这里摘结论：

| 指标 | 目标 | 实测 | 判定 |
|---|---|---|---|
| 系统调用额外延迟 | P99 ≤5μs | P50 +4.2μs，P99 +34.6μs（重尾） | 未达标 |
| 常态 CPU | ≤3% 单核 | 3.48% | 未达标 |
| 内存 RSS | ≤150MB | 252.5MB（30 分钟） | 未达标 |
| 事件吞吐 | 1 万事件/s 不丢高优 | 1 万 ops/s 下高优事件被 store 丢 15.6 万条，持续入库仅 ~4k 事件/s | 未达标 |

数字难看，但都是真的，而且每个未达标项都附了降级方案。压测还顺手抓到一个观测性缺口：内核态 ringbuf 满了以后 `reserve` 失败不算进 drop 计数器，60 万事件压进来，"入库加丢弃"对不上账的 32 万条无声无息。全速压测时甚至出现 events 表零入库、drop 计数零的干净假象。监控自己的可观测性有洞，这个优先级排在优化前面。

用例库侧的好消息：进程链缺失率为零，6 用例两轮 12 项验收全过；容器篡改告警的容器短 ID、runc 祖先链均有实证落盘（`/tmp/m01_evidence/`）。
